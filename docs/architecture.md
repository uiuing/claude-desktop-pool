# Architecture

`ClaudePool` (SwiftUI) composes `PoolCore`, `PoolRuntime`, `PoolPrivacy`, `PoolGateway`, and `PoolEngine`.

- PoolCore: typed account/quota/session state, request/event contracts, routing, localization.
- PoolRuntime: private owned workspace, credential-free metadata, official executable configuration, isolated authentication and owned PTYs. CPTY contains only the fork/exec terminal boundary.
- PoolGateway: authenticated literal-loopback HTTP, Anthropic Messages responses/SSE, model discovery and Desktop connection (`DesktopConnection`: Pool's profile in `Claude-3p/configLibrary`, applied in `_meta.json`, `deploymentMode` written last; a private record restores the previous settings on Disconnect; a key Desktop sealed at rest is treated as unknown, not changed). No outgoing vendor requests.
- PoolPrivacy: required local text inspection, stable conversation replacements, request-scoped restoration, model installation and bounded native inference.
- PoolEngine: conversation/account binding, official interactive worker, the reader of its own session transcript, hint-only hooks and the standard MCP helper. Clients receive tool calls; only the client executes them.
- ClaudePool: onboarding, pool dashboard, accounts, menu and settings. Demo never instantiates runtime services.

## Bridge contract

A backend receives a `BridgeRequest` plus optional explicit `conversationID` and yields `BridgeEvent` values. Each HTTP request ends on a `finished` event. A tool-call response ends with `tool_use` while its underlying official MCP call remains parked; a subsequent request returns the matching tool result to that run. The run is found by the calls' ids, while the request goes on from the conversation the run was told (`told`, set from the request it answers and compared by words, calls and results). The reply the run gave is not compared, so a client that keeps the reply its own way (its text before or after the call, its own wording) stays in the run; one that only took earlier images out does too. When earlier messages did change, `coordinator.diverged` logs the first message that differs by role and block kinds. A tool result is never refused because its run is gone, stopped, evicted, answered already or on another account: the request becomes a run of its own, told the whole conversation. Client-visible output is a commit boundary: never automatically replay an emitted answer or tool. Account handoff is allowed before new committed output for a confirmed account-specific limit, unavailable subscription/login or model entitlement. Policy/content refusals are returned unchanged in meaning. Unknown transport outcome is not safe to retry automatically.

Official helper events are atomic JSON files inside a mode-0700 run directory. Hooks observe and exit without modifying decisions. MCP calls wait on matching result files. Child account directories are stable; only the official CLI accesses credentials in them. Local metadata stores the official email and a scoped identity fingerprint to avoid counting the same subscription twice. Tokens and raw vendor identifiers are not stored by Pool. Route records contain opaque local IDs, not emails or prompt contents.

The native client receives a narrow documented `--allowedTools mcp__pool` grant for the forwarding transport. The helper itself executes no Desktop tool: Desktop still owns the actual action and its permission checks. The client's instructions follow the session's own system prompt (`--append-system-prompt-file`, the billing line removed): Anthropic has refused interactive turns whose system prompt a client replaced. The launch uses `--setting-sources ""`, settings with deep links off and Pool's status line, `--no-chrome`, and an environment (auto-compact, auto-memory, git instructions and nonessential traffic off, a one-hour prompt cache). `ENABLE_TOOL_SEARCH=false` keeps the session from hiding forwarded tools behind a search of its own, as the client already chose which are loaded. Built-in file, shell and external-action tools remain disabled, `--permission-mode default` remains active, and managed denials remain authoritative. The client's own conversation-termination control remains available. Each account has a stable app-owned working directory that only Pool's own children run in. By maintainer decision, Pool answers the official client's first-run screens there as a person would on first launch: the default text style, the security notes, skipping terminal setup and browser tools, and trusting that app-owned folder. A key is sent only after its screen has stayed drawn, at most three times per screen. Sign-in, permission, usage-credit and every other prompt remain the user's; a sign-in screen is reported as an authentication failure, never answered. The client records first-run completion and folder trust itself, so later workers and quota reads start directly.

A turn is read from the session's own transcript, (`ClaudeTranscript`): the file under the account's `projects` folder, read from its size at launch. A user row is the message taken; assistant rows carry the text, tool calls and usage; a `turn_duration` row ends the turn; a `<synthetic>` API-error row is the client's own error. Unknown rows are ignored, and hooks are hints that never fail a turn. A turn without usage ends with the usage seen, or zero.

A reply is told as it streams. Claude Code is a Bun program; `BUN_OPTIONS --preload` loads Pool's tap (`ClaudeTap`), which copies the main turn's reply stream to a private file of the run's, one JSON line an event, from a tee of the body Claude Code reads itself. Words go to the client as they stream, and each tool call once its input is whole, in the message's order, all of one message's calls in one reply, under Claude Code's own tool-use id (the MCP call's `claudecode/toolUseId`), so text written before a call is never told after its card and parallel calls are never split. Claude Code may write a message calling a client's tool only once the call is answered, so a call the helper hands over that no stream told within 500 ms is the reply itself (`ClaudeReply`); a message told whole is taken as whole after 300 ms of quiet. Results the client sends for a group of calls are held until Claude Code makes each call. A client that does not load the tap is told whole messages from the transcript, as before.

The client's `tool_choice` is told to the session: every tool is still offered so the prompt cache keeps its key; with `none` a call is answered in the session ("no tools now") and the turn goes on in words; `required` or a named tool is asked for in the instructions, a named one offered alone. A structured answer (`output_config.format`) is an answer tool: `StructuredOutput` with the client's schema (its root `$schema` dropped); a call that does not fit is told why, one that fits is the answer, the turn's words are left out, and a turn that ended without it is asked once. Web search is Claude Code's own `WebSearch`, offered and allowed for that run.

Messages are entered with no envelope. Client text is made typeable: CRLF and CR become new lines and other terminal controls are removed; text starting with `/`, `!`, `#` or `&` gets a new line first. A run is ready when its input box is drawn and the MCP helper has listed its tools, within one 45-second wait, then 300 ms. The bracketed paste is waited for (its last line's end in the output since the paste, 10 seconds plus one per 64 KB), and Return is pressed on its own even if it was not seen. Until the transcript shows the message taken, Return is pressed again every 3 seconds, at most four times. The reply deadline starts once the message is taken.

A conversation no live run holds is not pasted. Pool writes the session Claude Code itself would have written up to the last reply that called no tool: two transcript lines, the history before it as one user message (in a `<conversation_history>` form, images as image blocks) and the reply's words, in the account's project folder for the run's real working path. The run starts with `--resume` on it, and only the messages after that reply are typed. A resumed start that fails is started once more with the conversation told whole. The file is the run's own and is removed with it.

An error the client reports passes on as follows: a known Anthropic status as it is, Claude Code's own "Prompt is too long" and any other overflow as a 400 the client compacts on, quota words as a limit, anything else as 502. The gateway holds a stream's headers until the first of the answer, so an error before it is a real status; after it, an `error` event ends the stream. 503 means only a moment's wait (busy, no room, quitting); a session that ended without an answer is 502 and local redaction that is not ready is 400. A failed reply is never cancelled by the gateway, so its retry finds it settled. A permission or elicitation dialog fails the reply at once with an actionable error; Pool never answers it. Cursor-position and device-attribute queries get an ordinary terminal's fixed answers.

A reply that is stopped or fails ends its run: the run never takes another turn. It is closed normally, with the client's own interrupt keys if `/exit` cannot be typed, when its conversation returns, when room is needed for another conversation, or by the idle timer. The conversation's next request starts a new run with the full client history. A refusal for a limit without proof of which limit is not quota evidence and never parks the account: it rests for 60 seconds and its usage is read at once; that reading decides whether it is limited.

Pool sets no bound on how many Claude Code processes run at once and does not check memory before starting one: macOS compresses and swaps memory itself, a process takes some 170-205 MiB of physical footprint, and a bound read from memory only held conversations back. The dashboard, the menu panel and Settings show how many run. Idle runs are shelved after five minutes and runs waiting on tools end after an hour, which is what gives memory back.

A run that finds the room full waits for one to come free, with two special cases. The last of the room, up to two places, is for one-off asks: a tool call in auto mode waits on the classifier, which needs a process, so a room full of runs waiting on calls would otherwise hold it out until one had waited `parkLongest`. A released run stays for its client's results but gives up its room at once when another needs it, because a result that comes later is replayed in a new run. A request that has waited two seconds for room is told to the app, which shows how many requests wait, on every page and in the menu panel, with the way to allow more. The Pool page and the menu panel also show how many processes run of how many may, and say that each conversation, each subagent and each short ask takes one.

A new conversation goes to the account with the best `PoolRouting.score`: the 5-hour and weekly shares left weigh about the same (0.45 and 0.40), a 5-hour limit near its reset counts for up to half of what it has used, a week within two days of its reset adds its unused share (0.15) so it is spent before it lapses, and each conversation already on the account takes 8 points off. A conversation stays on its account for its prompt cache: by its client session, and, when Desktop starts a new client session for it after an error or a restart, by a content-free tag of its first exchange. Both are kept for the idle hour and saved at quit (`conversation-accounts.json`, tags and account ids only). A run that cannot take its conversation's next turn is ended and the turn goes on in a new run on the same account; a run that does not end is kept for the user and the turn is not refused. Each held close logs `session.close_held` with its reason.

The gateway routes on the path alone, so Claude Code's `?beta=true` reaches `/v1/messages`. `/v1/models` lists each pool model by the official client's id and name for what its alias runs (`PoolModel.listedID`, from the last `ModelIdentity` a session's status line reported, else this build's), tagged `anthropic_family_tier`; replies name the id the client asked for. Full model ids (`claude-sonnet-4-5-20250929`, `claude-opus-4-1[1m]`) resolve by family. Desktop's connection check (one user "." for `max_tokens` 1 and nothing else) is answered from `BridgeBackend.checkAdmission`: an empty single-token reply when an account could take a request now, else the failure (`429` with `Retry-After` when every account is at a limit); no session starts for it. Requests are taken in the shape Desktop's Code tab sends them (`ClientRequestShape`), modelled in tests on Claude Code's real requests rather than the plain Messages shape. Nothing is refused for asking more than the interactive client can apply. Sampling hints, reasoning budget and `thinking.display`, effort, context editing, auto mode's `safeguards`, `speed`, stop sequences, `mcp_servers` and `container` are not applied. A block of a kind the session has no use for (documents, server tool records, search results) is left out, and so are a tool result's parts other than words and images. A server tool is not offered: web search is noted (`BridgeRequest.webSearch`), and the advisor's instructions in the conversation are said to be void. `tool_choice` is kept (`none`, `required`, `name:<tool>`), and so is a structured answer's schema (`output_config.format`). A request's `tool_choice`, web search and schema are part of its conversation's key, so a title or summary asked with `tool_choice: none` of a long conversation is a conversation of its own. A refusal the gateway still makes (malformed JSON, no messages, an unknown model) is logged with the first words of its fixed text as its rule. A `{"role":"system"}` message inside `messages` carries a turn's effort (dropped) and at times text, which joins the user turn it came with so the session's instructions stay the same. Thinking blocks in earlier answers are the service's record and are dropped. Deferred tools follow the client's own tool search: a `defer_loading` tool is offered to the session only once ToolSearch answered with a `tool_reference` naming it or a `tool_addition` brought it, and no longer after a `tool_removal`; ToolSearch's answer reaches the session as "Tool X is loaded and can be called now." The service's own tool-search tools are dropped. Connect seeds `toolSearchEnabled: true` in Pool's own Desktop profile when it has no value (a value the user set, false too, stays theirs): off, Desktop starts Claude Code with its experimental betas off and every MCP tool's full schema goes with each request. Pool also sets `desktopHome: standard` when the profile has none, so Desktop shows Chat and Cowork; unset, Desktop decides from its older per-tab keys, which leave Chat off. A profile missing either key reads as outdated until Connect writes it again. A profile an earlier version wrote without it reads as outdated, and the menu offers Update, which is Connect again. Cache hints and Claude Code's per-request billing line are removed before anything compares or stores a conversation, so they neither break affinity nor become instructions. A client session id is a namespace: each shape of instructions, always-offered tool names and model inside it is its own conversation, so side requests (titles, suggestions) neither wait behind nor replace the main one, while deferred tools loading within a conversation keep it one. A pool account that must sign in again returns 403, never the 401 that means a bad gateway key; a limit with an official reset carries `Retry-After`. Usage includes measured cached input.

Only one copy of the app holds the workspace (an exclusive lock on its root). A second copy brings the first forward and quits, so two copies never sign accounts in and out under each other's sessions.

Deferred tool discovery updates the atomic private catalog at a validated tool-result boundary. Names keep their aliases across additions, removals, reordering and schema changes. The MCP helper advertises `listChanged`, sends `notifications/tools/list_changed`, and acknowledges the exact revision after answering `tools/list`. Pool waits at most 5 seconds for that acknowledgment, then releases parked tool results anyway, and the helper takes a call for any name in the listed or the current catalog. Already accepted calls retain their own result identities. A new run that finds it full ends a stopped run, lets go of the run idle longest, else of one that has waited 5 minutes on tool calls, and otherwise waits for one to end, two minutes at most, before its request is answered busy (`coordinator.room` logs the wait). A run waiting for its conversation's next turn keeps its process five minutes and is then shelved for the rest of the hour its prompt cache lasts; six such runs are kept (the five minutes are chosen because a shelved session resumes on the same cached prefix). A conversation is remembered on its account for the hour its cache lasts, set when a run for it starts (so a handoff moves it at once) and renewed at each reply; a conversation whose run has ended for any reason goes back to that account while it can take it above the reserve (Pool's own). A run let go for room or past six is shelved: it ends normally and its Claude Code session is kept, by its conversation up to the last reply, model, instructions and tools, until its hour is out (64 at most). That conversation's next turn starts a run on the same account with `--resume` on the session, told only the turn since, so the service is asked a prefix it has cached; an account that can no longer take it, a conversation edited since or other instructions or tools discard the session and the turn goes as any new one (`coordinator.route` `shelved`/`unshelved`). A run waiting on tool results gives way after 5 minutes when room is needed or more than 16 wait, and any run ends after an hour, as long as its prompt cache lasts (a subagent or a long command is one call, and a run let go before its result has its whole conversation written to the cache again). A late result then becomes a run of its own.

After every pending result has been validated and accepted by its original worker, a confirmed account failure before new output can hand off the completed history. Only the coordinator can construct that replay; an incoming request cannot authorize it with a flag. The new worker receives ordinary context describing already completed actions. Pool does not resend those actions to Desktop. Partial results, cancellation, content refusals and ambiguous failures do not enter this path.

Quit ends the pool's own Claude sessions without asking anyone to end them first: an idle session takes the client's `/exit`; one answering, waiting on a tool or holding input has its request cancelled and receives the client's own Ctrl-C, never a forced end. Sessions and quota observers end at the same time, and from then on nothing is admitted, tool results included, so no run starts after the others ended. A small panel says quitting is under way from the moment it begins; `app.quit` logs the start, the duration and the reason for a refusal. A Ctrl-C that finds the child already gone counts as its exit, not as a failure to end it. The gateway then gives open replies three seconds. Only an unfinished sign-in or account check, or a child that does not end, keeps the app open. Native `SessionEnd` is a lifecycle notification, not proof that a process exited. Account changes and normal shutdown retain the owned child until PTY exit is confirmed. Only then can Pool remove that run's known temporary IPC files. Cleanup failures retain the private directory and allow a closing retry. Native account configuration and other runs are outside this cleanup boundary.

Pool keeps an app log: `~/Library/Logs/Claude Pool/pool.log`, mode 0600 in a 0700 folder, moved to `pool.old.log` at 10 MiB. It is built so a problem can be explained from the log the first time it happens, not after logging is added for it:

- **One id per thing.** Runs and accounts are written as `Diagnostics.id`, the first eight characters of the lower-case UUID, as the account folder and the client's session file are named, so one run or account can be followed through every event and found on disk. Conversations are a short hash.
- **Every state change, where it is published.** `coordinator.state` (each run: from, to, busy, pending calls, stopped, retiring), `quota.state` (each account's read phase and failure, retry delay), `account.state` (each account's state and plan, from the one place the library changes). A value is written only when it changes.
- **Every decision with its reason and inputs.** `coordinator.decision` for each routing reason, `coordinator.pick` with the account chosen, whether the conversation kept its account, and the leading candidates' scores and loads; `coordinator.route` for replays, replacements and shelving; `quota.read`, `warmup.sent` and `gateway.request` with outcome and timings.
- **Watchdogs for silence.** A reply that hears nothing from its client for 90 seconds logs `session.stalled` (what it waits on, calls and results pending) and `session.resumed` when the client is heard again. `coordinator.health` every five minutes while runs exist counts them by state, with the longest busy and parked.
- **A flight recorder per run.** Each run keeps its last 64 steps in memory (reply opened, results delivered, hooks, stream and transcript markers, input typed, finish) and writes them as `session.trace` lines only when it fails, stalls or cannot close, so the lead-up is there without logging every step of healthy runs.

Lines hold fixed names, counts, sizes, timings and ids Pool made. Message, system and tool text, tool names and inputs, screens, emails, keys and project paths are never written, and a credential-shaped scrub backs that up. New code follows the same rules: a new state is logged where it is published, a new decision with its reason, and a new wait gets a watchdog. Settings shows the file in Finder.

Per-child documented controls disable automatic `@file` expansion and CLAUDE.md/auto-memory loading. This prevents forwarded client text from reading host files or importing unrelated host instructions. Explicit images remain validated app-owned attachments. Desktop owns conversation persistence. A run's session transcript is the account folder's own, read by Pool for the turn and removed with the run; Pool writes one only as the saved session a replay resumes, never edits one the client wrote. These controls do not disable OAuth or Keychain authentication. See the official [environment variables](https://code.claude.com/docs/en/env-vars), [MCP permissions](https://code.claude.com/docs/en/permissions#mcp), and [dynamic tool updates](https://code.claude.com/docs/en/mcp#dynamic-tool-updates) contracts.

## Managed runtime

Pool downloads immutable official Claude Code releases to its own workspace, verifies manifest size, SHA-256 and native architecture, and activates a version atomically. Existing workers keep their original executable. Future workers use the current managed version. The app does not install global shell launchers, change PATH, use a package manager, or alter another client's update settings. Documented updater controls apply only to Pool's children. Settings offers the previous version only after its installation passes verification again. Installation, loading and rollback require at least version 2.1.299 for the documented file-mention isolation control; callback validation remains necessary on every session.

## Application lifecycle

New sign-ins remain in memory until the official client returns a valid identity. Closing or cancelling a provisional sign-in interrupts only its owned process, waits for normal exit, and uses official logout before clearing the provisional state. Existing verified accounts remain saved across failed reauthorization. Legacy rows without a verified email are removed from the local library on load. Sign-in runs `auth login --claudeai` in a PTY. A pasted code is entered as a terminal enters it: bracketed only after the child enables bracketed paste, with Return sent separately once the text has been taken in. Identity comes from `auth status --json` on plain pipes, because a terminal receives that document rendered with cursor controls and hard wraps. A completed sign-in closes its terminal and names the account. A failed one keeps its ended output visible with the reason and a retry; only an explicit close or retry dismisses that view.

The managed runtime publishes release resolution, byte-based download progress, verification, activation and completion separately. The installed version remains distinct from the target version. A credential-free receipt records the day's official release check and any available version. Startup and application activation may check once per local calendar day; manual checks bypass that schedule. A failed check preserves the installed version and the last known available update, with a retry message.

Appearance preferences persist as system, light or dark and apply to the main window, menu and sheets. The app declares a regular foreground role. It uses regular activation policy while its main window is open or minimized; closing the window switches to accessory policy, leaving only the menu bar item, and any request to show the window returns to regular policy before activating. Main and terminal windows do not hide on deactivation; the menu remains a normal transient menu. Menu Quit calls normal application termination through the same delegate shutdown, which ends owned sessions itself. Terminal links are parsed from raw PTY chunks before display wrapping, kept in memory, and opened or copied only on explicit user action. Clipboard and browser actions receive the complete URL rather than the abbreviated display label.

## Quota lifecycle

Inference status-line observations and separate official `/usage` observers feed the same quota state. Refresh never types commands into a user's inference session. Timed reads come only from session activity: an account with no recent work has no interval at any pool size. When its work decays to nothing, one `settle` read follows if the account worked after its last reading. An account that starts generating after two quiet minutes, or that the app names as next in line while an account in use is within 15 points of the reserve (at most three such reads in ten minutes), gets a `selected` read when its reading is ten minutes old or more. Opening the menu starts no read. Quiet sign-in checks cover only the accounts in use and the next one; others are checked when chosen or on request. A quota session held for the user is that account's refresh; another request does not queue behind it. An automatic failure keeps such a session for the user, but an explicit exit, quit or account change ends it: a session that has not reached its idle prompt cannot take `/exit`, so it receives the client's own double Ctrl-C, at most twice, and is never forced. At quit, an observer whose panel or `/exit` did not end it gets the same Ctrl-C. A child that still does not end is reported and retained. Attention from a previous app run does not block the next launch's initial read. At launch, with a usable managed client, each signed-in account that has never been read gets that one initial read even while the pool is stopped; this is not periodic polling. Initial sign-in, manual actions, account changes, bounded error recovery and each official reset can trigger a read; a persisted reset receipt prevents repeated reads of the same completed boundary. Periodic reads use actual session activity, not merely the existence of a retained worker. Scheduling pauses while asleep, locked or offline, respects authentication failures and account-specific backoff, and rechecks fresh evidence before launching an observer.

The coordinator publishes scoped counts and state transitions, never response bodies, to the cadence controller. Distinct official completions provide turn frequency; native output deltas and measured token counts provide throughput. A 15-second EWMA smooths those signals, and quiet periods decay them with real elapsed time. Each generating session contributes at least one demand unit; its frequency/throughput signals can raise that contribution. Concurrent sessions add demand. Waiting for tools/users and completed work have no generating baseline and only bounded recent-work tails. No recent activity means no periodic interval.

The controller interpolates geometrically between five internal timing points at demand 0, 0.5, 1, 2 and 4: 300, 120, 45, 20 and 10 seconds. They are not shown to the user. `QuotaBurn` then measures each every-model limit's pace from successive official readings of one cycle (forgetting it at a new cycle) and moves the interval by at most a factor of three toward a sixth of the time left before the switch threshold, between 10 seconds and 10 minutes. An account read again within a minute keeps its usage session at the prompt (the panel closed with Esc) for up to 90 seconds; reading another account, sleep, going offline, quit or any account change ends it normally. A fast single session can reach the fastest point through its completion frequency or throughput. Actual official quota readings defer an extra query; duplicate progress never increases activity. One usage observer runs at a time, with at least 10 seconds between automatic attempts for an account and 2 seconds after another observer closes. Manual requests keep their 30-second throttle. These timers regulate observation only; they never estimate quota or reset time.

Reset timestamps come from the official client; no reset is predicted. Confirmed inactive-cycle readings retain their original observation time and remain usable before the official reset. A window whose stated reset has passed (or, without one, a full span after its reading) is renewed: it counts as full and stops blocking at once, and a read 60 seconds after the reset confirms it; a reading that still shows the ended cycle is retried after 60·2ⁿ seconds, up to 15 minutes and six attempts. `AccountStanding` orders and counts accounts: usable, unread, limited, week used up, unavailable; every non-duplicate account feeds totals. Only accounts in rotation (`PoolAccount.isInRotation`: ready or limited, week not used up) get automatic reads: timed, settling, selected, reset-confirming and failed-read retries all skip the rest, and a queued automatic read is dropped once its account leaves rotation. To show when an exhausted account's constraints reset, Pool takes the latest official blocking reset for that account. A pool-level time is the earliest of those confirmed account boundaries, with unknown constraints kept separate.

An official-client report of a changed email, organization scope or plan clears old-scope quota before publishing the new state. Explicit Free is subscription-required, not a failed login or a guessed downgrade. Unknown or failed account reads never become Free. The official client owns credential renewal. Reauthorization and removal use its own login/logout commands in the isolated environment; Pool never extracts or refreshes tokens itself.

`WarmUpScheduler` looks once a minute (first two minutes after launch, and at once on waking) and asks `WarmUpPlanner` what is due: the every-model 5-hour and weekly limits that are not running on an account that can serve, per the warm-up settings. One account at a time runs the official interactive client on its Haiku alias for one short fixed prompt in its own account directory, then closes it; the session's status-line limits are taken as a reading, else the account is read. What was sent is kept exactly (`warm-up.json`), so a stretch is warmed until a request starts it, retried after 15 minutes doubling to four hours and given up after six requests until the next reset, and each set time is served once within its hour. A limit reading 0% with its whole span but ten minutes still ahead counts as not started, as Claude can report one nobody used as starting now.

## Usage ledger

Usage is counted where the reply is served, one record per call, not by scanning transcripts, which Pool removes after a run. When a reply's usage first arrives, the coordinator publishes `EngineUpdate.usage` once for that attempt: the account scope, the model's listed id and name, the official client's token counts and the time. A failed attempt that already reported usage stays on its own account, so a failover never moves spent tokens. Counts come from the transcript row or the reply tap: input, output, cache read, cache creation, and `cache_creation.ephemeral_1h_input_tokens` as the 1-hour share of the writes. A reply with no tokens adds nothing; negative counts are zero, and 1-hour writes never exceed the writes.

`UsageLedger` keeps one entry per local day, account and model: the token counts, the reply count, the estimated cost, the cost with every cached token priced as input, and the number of unpriced replies. Hourly tokens are kept for today and yesterday only. Days older than 400 are dropped. No prompt, reply, conversation id or email is stored; accounts are their UUIDs, and a removed account's history stays as "Removed account". `UsageStore` writes `usage.json` in the app's workspace 30 seconds after the first unsaved reply and at quit. A file this version cannot read starts an empty ledger rather than blocking the app, since it holds statistics only.

Cost is an estimate at Anthropic's first-party API list prices (`ModelPricing`, checked 2026-10): the whole call at the tier its prompt reaches, cache reads at the model's read price, 5-minute writes at 1.25x input and 1-hour writes at 2x input (`OneHourFor`). Pool reads no price online. A model the table does not know counts its tokens and is shown as unpriced. Subscriptions are not billed per token, and the page says so.

The Usage page reads one `UsageSummary`, computed again only when the ledger, range (today by hour, 7 days, 30 days, all), account or model filter, grouping or hour changes. Comparisons are with the same span just before; today is compared with yesterday up to the same hour. The chart stacks by model, plan (each account's plan now) or account, colours the five largest series and folds the rest into one, so a pool of a hundred accounts stays readable. The account list is ranked, searchable, sortable and paged; plan totals above it narrow the page to a plan. The chart and sparklines are Canvas drawings.

## Local sensitive data redaction

`PrivacyBridge` wraps the coordinator and runs the local AstrLink Guard model. Every supported text category is enabled. AstrLink Guard starts from the built-in 0.1.3 release. Once a day Pool reads the publisher's newest `vX.Y.Z` tag, resolves its commit, requires an Apache-2.0 license and the same 21 token labels, and downloads that release's INT8 files beside the one in use, each checked against the release's `int8/CHECKSUMS.json`. The new model must load and answer before `privacy/current.json` switches to it; detection continues on the old one meanwhile, and the previous release's files stay until the next update. The artifacts are size/hash checked and run through Microsoft's pinned ONNX Runtime 1.24.2, with two CPU threads and no remote inference. A request waits at most 2 seconds for the model to read what is new in it; past that it goes with what the model found and the rules for the rest (`Partial`), and only the chunk being read for it is finished (`Bounded`). What the model read is kept by digest, so a later request finds it. Of text sent earlier without the model's reading, a request reads at most one 4 KB chunk after its own (`backlogCap`); nothing is read in the background. Texts are read newest first, joined into chunks, a long one in overlapping pieces, and of the requests waiting the one with the fewest bytes left goes next (`queue.next`). Two detections run at once and the rest wait in order; nothing is refused or timed out in that queue. A model that fails is not asked again for a while (30 seconds, doubling to 10 minutes) and the rules mask alone meanwhile. Model memory is released after idle time.

The detector supplies validated UTF-16 spans; rules cover explicit credentials and structured personal data. Model spans are taken selectively: only its person, address, phone, email, account and secret labels (its date and URL labels are left out, card numbers and IP addresses are the rules'), trimmed of the spaces it takes in and, but for a secret, of quotes and separators, and dropped when cut from a longer word or not of their kind's shape (a name with no letter, a phone with fewer than seven digits, a secret under eight bytes). Conversation-specific HMAC replacements remain stable for previously sent history, while new occurrences are inspected with newly learned values: a value masked once is masked again in later text only when it has at least eight bytes and stands alone there. Each preparation tracks only its own text and numeric cache entries; an HTTP request commits them when its backend first produces an event. Failed or cancelled drafts remain eligible for inspection. Detection caches contain digests and spans rather than additional plaintext copies. Original values exist only in the in-memory restoration map. Messages, tool values and schema descriptions/defaults/examples/enum data are inspected; IDs, tool names and structural schema fields retain their protocol meaning. Sensitive safe integers use reversible numeric stand-ins, preserving JSON types.

Stand-ins are numbered: Pool holds each conversation's values, so a stand-in is a number within the conversation (`{{API_KEY_1}}`), not a hash. What the model acts on keeps its shape (`user-1`, `host-1`, `public-ip-1`, `bucket-1`); what it only carries is a tag. A stand-in's own words in a text are masked as a value, so a reply repeating them comes back as written, and a number no text has said is the one used. Nothing is added to the system prompt: a stand-in's shape alone says what it is. Reviews and the per-conversation mask cache are held to a byte budget; a text sent unchanged is kept as a marker, not a copy.

Output restoration puts back only a replacement the active request carried. A placeholder split across stream fragments is held until it is whole; one this request did not carry, an unclosed one at the end or one longer than 128 characters passes through as the model wrote it, and so does a numeric stand-in the request did not carry. Text that already has a placeholder's shape (`{{CP_…}}`) is sent as it is and nothing is masked inside it. A block of a kind redaction does not know is walked block by block: its protocol fields kept, its other values masked. Image bytes are passed unchanged, matching the text-only scope. A failing or slow model never holds a request: the rules mask what it has not read. When the restoration map is full, entries no request has sent yet are let go first. Counts and categories drive UI statistics without logging input or originals. Claude sessions are the pool's own: the app offers no way to open, switch or type into one; the route view follows the conversation working now. Quota observers accept navigation controls, while official account sign-in retains its normal credential entry. While the outbound request is produced, the fields new in it that had something replaced are recorded as segments (plain text, or an original with its placeholder) and published once per request as a `PrivacyReview`; long text keeps 240 characters of context around each replacement. Reviews and their put-back counts live only in the app's memory, at most 40, and never reach disk, logs or diagnostics.

Cancellation marks a protected request inactive before awaiting its owned backend and before dropping the request identity. That ordering closes manual-input authorization immediately and keeps stream cancellation from losing its target. Privacy previews use separate ephemeral state and cannot repopulate a sheet after dismissal.
